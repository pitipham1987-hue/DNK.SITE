🔐 Trust Zones & Boundaries
🌐 Zone 1: Browser Client
Trust Level: Untrusted
User can inspect/modify anything via DevTools.

Lives here:
• HTML pages (index, contact, blog, admin)
• CSS (tokens → base → components)
• Vanilla JavaScript (IIFE pattern)
• localStorage (contact log only)
• OAuth tokens (in memory)
• Anon key (safe via RLS)
Zone 1
🔗 Zone 2: HTTPS Transport
Trust Level: Encrypted but inspectable
User can see all requests/responses in Network tab.

What crosses here:
• OAuth tokens
• REST API calls
• Database mutations
• Image uploads

Protection:
HTTPS prevents MITM; Supabase enforces CORS
Zone 2
🛡️ Zone 3: Supabase Backend
Trust Level: Trusted — RLS enforces all access

Lives here:
• PostgreSQL (profiles, categories, posts)
• Auth tokens + Google OAuth delegation
• Storage (post-images bucket)
• Service role key (offline, never in code)

Security Gate:
is_admin() PL/pgSQL function checks JWT role claim
Zone 3
🚨 Key Security Principle

The browser never makes access control decisions. It calls Supabase REST with a token. The RLS policy says "yes" or "no". No validation logic duplicates between frontend and backend — PostgreSQL is the source of truth.

⚙️ 10 Core Components
1️⃣ Browser Client
Renders all pages (index, about, services, contact, blog, admin). Loads CSS cascade (tokens → base → components → admin). Executes JS modules. Stores contact form locally. Initiates OAuth redirect.
2️⃣ Public Pages (HTML)
index.html: Hero, features, pricing, insights (3 blog posts)
about: Company mission
services: Service details
contact: Form + localStorage
blog: Post detail by slug
3️⃣ Admin Dashboard
Google OAuth login → role check (is_admin) → blog CRUD. Single-page: login → dashboard → editor. Create/edit posts: title, slug, excerpt, category, cover image (upload), Markdown. Soft-delete + restore.
4️⃣ CSS System
tokens.css: Colors, spacing, typography, motion
base.css: Typography, layouts, utilities
components.css: Buttons, navbar, sections, forms
admin.css: Admin-specific styles
5️⃣ JavaScript Modules
main.js: Scroll-reveal (IntersectionObserver), sticky navbar, mobile nav toggle
contact.js: Form validation, localStorage logging
blog.js: Fetch posts, custom Markdown parser
admin.js: OAuth, role check, CRUD
6️⃣ Supabase Config
supabase-config.js:
Project URL + public anon key (exposed — safe via RLS).
Attached to window.DNK_SUPABASE global.
Never contains service_role key.
7️⃣ Supabase Auth API
Google OAuth Delegation:
Supabase manages flow (Google provider).
User logs in via Google → redirects back with #access_token=...&refresh_token=...
admin.js captures hash, verifies token.
8️⃣ Supabase REST API
All data queries routed through /rest/v1/* endpoints.
No custom backend.
Public endpoint for blog reads (published posts only).
Admin token required for CRUD (enforced by RLS).
9️⃣ PostgreSQL Database
profiles: id, role (admin|reader), display_name, created_at
categories: id, name, slug (regex), created_at
posts: id, title, slug, excerpt, content (Markdown), cover_image_url, status, published_at, deleted_at (soft delete), author_id, category_id, created_at, updated_at
Index on (status, published_at desc) for fast queries.
🔟 RLS Policies & Storage
post-images bucket: Public read, admin-only write.
RLS Policies:
• Public: Read categories + published posts
• Admin (is_admin()): Full CRUD
• Users: Own profile only
Triggers: auto-set updated_at, auto-create profile.

🗄️ Database Schema & Row-Level Security

Tables

Table Columns Key Features
profiles id (UUID), role (enum), display_name, created_at 1:1 with auth.users. Auto-created on signup. role: admin|reader.
categories id (bigint), name (unique), slug (regex), created_at Blog post categories. Slug validated: ^[a-z0-9]+(?:-[a-z0-9]+)*$
posts id (UUID), title, slug, excerpt, content (Markdown), cover_image_url, category_id, author_id, status, published_at, deleted_at, created_at, updated_at Soft delete via deleted_at. Index on (status, published_at) for speed. updated_at auto-set on mutation.

RLS Policies (Access Control)

Policy Role Permissions
Public Read Anonymous + Auth Read categories. Read published, non-deleted posts.
Admin CRUD is_admin() = true Full CRUD on profiles, categories, posts. Write to post-images bucket.
User Profile Authenticated Read/update own profile row only.

Database Triggers

Trigger Event Action

🚀 Deployment & Setup

Local Development

python -m http.server 8000
Then open http://localhost:8000

Why HTTP server? Relative paths + Google Fonts require proper HTTP serving (not file://).

Production

  • Static files served via HTTP server (Vercel, Netlify, AWS S3 + CloudFront, etc.)
  • No build step: upload HTML/CSS/JS as-is
  • Asset paths: index.html uses assets/..., pages use ../assets/...

Supabase Configuration

  • Supabase URL + anon key in supabase-config.js (hardcoded, safe via RLS)
  • No .env file needed (no build tool)
  • OAuth Redirect URLs registered in Supabase Auth → URL Configuration
  • Dev: http://localhost:8000/admin/
  • Prod: https://yourdomain.com/admin/

Database Migrations

  • Migration: supabase/001_admin_blog.sql
  • Run once via Supabase Dashboard (SQL Editor) or CLI: supabase db push
  • Creates tables, indexes, triggers, RLS policies, Storage bucket
✨ Architecture Promises
🚫 No Backend to Run
Supabase handles auth, database, storage. No server maintenance overhead.
⚡ No Build Step
Ship HTML/CSS/JS as-is. No webpack, vite, or npm needed.
🛡️ Security by RLS
Trust the database, not the frontend. All access decisions made at PostgreSQL layer.
📱 Mobile-First
Responsive design, scroll animations (IntersectionObserver), prefers-reduced-motion respected.
⚙️ Fast & Simple
Vanilla JS (~10KB code), ~50KB CSS (unminified), no framework overhead.
🔐 Admin-Protected
Google OAuth + RLS enforces role checks at every database operation.
🎯 Key Insight
💡 The Core Principle

The browser never makes a decision.

It calls Supabase REST, sends a token, and the RLS policy says "yes" or "no".
No validation logic duplicates between frontend and backend.
PostgreSQL is the source of truth.

This architecture eliminates the largest source of security bugs: frontend/backend logic divergence.
